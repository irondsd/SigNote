# Self-hosting Guide 🚀

This guide walks you through running SigNote locally for development or self-hosting.

---

## Prerequisites

- **Node.js** 18 or later
- **PostgreSQL** 14 or later — a local instance (a `docker-compose.yml` is included) or a hosted one such as [Supabase](https://supabase.com) or [Neon](https://neon.tech)
- **WalletConnect project ID** — get one free at [cloud.walletconnect.com](https://cloud.walletconnect.com) (required for SIWE)
- **Ethereum wallet** — MetaMask, Coinbase Wallet, or any wallet supported by RainbowKit (required for SIWE)
- An **Ethereum RPC URL** — Infura, Alchemy, or a public endpoint (required for SIWE)
- **Google OAuth credentials** (optional) — set up at [Google Cloud Console](https://console.cloud.google.com) if you want to support Google sign-in

---

## 1. Clone and install

```bash
git clone https://github.com/irondsd/signote.git
cd signote
bun install
```

---

## 2. Configure environment variables

Copy the example file:

```bash
cp .env.local.example .env.local
```

Then fill in `.env.local`:

```bash
# Required for all deployments
NEXTAUTH_URL="http://localhost:5000"
NEXTAUTH_SECRET="replace-with-a-long-random-secret"
DATABASE_URL="postgres://<user>:<password>@<host>:5432/<database>"

# Required for SIWE (Sign-In with Ethereum)
NEXT_PUBLIC_WALLETCONNECT_PROJECT_ID=""
NEXT_PUBLIC_RPC_URL=""

# Optional: for Google OAuth support
GOOGLE_CLIENT_ID=""
GOOGLE_CLIENT_SECRET=""

# S3 file storage
AWS_S3_BUCKET=""
AWS_S3_REGION=""
AWS_ACCESS_KEY_ID=""
AWS_SECRET_ACCESS_KEY=""
AWS_S3_ENDPOINT=""        # Optional: for S3-compatible providers (e.g. Cloudflare R2)

# Cron job secret
CRON_SECRET=""
```

**Core variables:**

| Variable          | Description                                                              | Required |
| ----------------- | ------------------------------------------------------------------------ | -------- |
| `NEXTAUTH_URL`    | Exact public origin — **must match** what you use in the browser         | Yes      |
| `NEXTAUTH_SECRET` | Secret used by NextAuth to sign session tokens (make it long and random) | Yes      |
| `DATABASE_URL`    | Postgres connection string                                               | Yes      |
| `PG_POOL_SIZE`    | Max pooled connections (default 10)                                      | No       |

**SIWE (Sign-In with Ethereum):**

| Variable                               | Description                                           | Required |
| -------------------------------------- | ----------------------------------------------------- | -------- |
| `NEXT_PUBLIC_WALLETCONNECT_PROJECT_ID` | WalletConnect project ID from cloud.walletconnect.com | Yes      |
| `NEXT_PUBLIC_RPC_URL`                  | Ethereum RPC endpoint (Infura, Alchemy, or public)    | Yes      |

**Google OAuth (optional):**

| Variable               | Description                               | Required |
| ---------------------- | ----------------------------------------- | -------- |
| `GOOGLE_CLIENT_ID`     | OAuth 2.0 Client ID from Google Cloud     | No\*     |
| `GOOGLE_CLIENT_SECRET` | OAuth 2.0 Client Secret from Google Cloud | No\*     |

\*Only required if you want to enable Google OAuth sign-in. SIWE works without Google credentials.

**S3 file storage:**

| Variable                | Description                                                                        | Required |
| ----------------------- | ---------------------------------------------------------------------------------- | -------- |
| `AWS_S3_BUCKET`         | S3 bucket name where files are stored                                              | Yes†     |
| `AWS_S3_REGION`         | AWS region (e.g. `us-east-1`)                                                      | Yes†     |
| `AWS_ACCESS_KEY_ID`     | AWS access key ID                                                                  | Yes†     |
| `AWS_SECRET_ACCESS_KEY` | AWS secret access key                                                              | Yes†     |
| `AWS_S3_ENDPOINT`       | Custom endpoint URL — set this to use an S3-compatible provider like Cloudflare R2 | No       |

†Required to enable file attachments. Without these, file uploads will fail.

**Cron job:**

| Variable      | Description                                                                                                         | Required |
| ------------- | ------------------------------------------------------------------------------------------------------------------- | -------- |
| `CRON_SECRET` | Secret used to authenticate the cleanup cron job that hard-deletes files from S3 after the soft-delete grace period | No       |

### Setting up Google OAuth (optional)

If you want to support Google sign-in, follow these steps:

1. Go to [Google Cloud Console](https://console.cloud.google.com)
2. Create a new project (or select an existing one)
3. Enable the Google+ API
4. Create an OAuth 2.0 credential (type: Web application)
5. Add authorized redirect URIs:
   - For local dev: `http://localhost:5000/api/auth/callback/google`
   - For production: `https://yourdomain.com/api/auth/callback/google`
6. Copy the Client ID and Client Secret into `.env.local`

> ⚠️ `NEXTAUTH_URL` is used by both SIWE and Google OAuth to validate the origin. It must exactly match the URL you use in the browser. For local dev, use `http://localhost:5000`.

## 3. Set up the database

If you don't have a Postgres already, the repo ships one:

```bash
bun run db:up    # Development Postgres on :5434
```

Then point `DATABASE_URL` at it and create the schema:

```bash
DATABASE_URL="postgres://signote:signote@localhost:5434/signote"   # in .env.local
bun run db:migrate
```

Migrations live in `drizzle/` and are generated from `src/db/schema.ts`. If you change the schema, run `bun run db:generate` and commit the SQL it produces — migrations are never hand-written, and they are not applied automatically at boot.

While iterating locally you can skip the migration file entirely and sync the schema straight into your database:

```bash
bun run db:push
```

Every `db:*` command targets the database in `.env.local` and prints the host it resolved before doing anything. The `:prod` variants (`db:push:prod`, `db:migrate:prod`, `db:studio:prod`) read a separate, gitignored `.env.prod` instead — so hitting production is always something you typed on purpose.

---

## 4. Run the dev server

```bash
bun run dev
```

Open [http://localhost:5000](http://localhost:5000) in your browser.

---

## 5. Sign in and set up encryption

1. Click **Sign in** and choose your authentication method:
   - **Sign in with Ethereum** — connect your wallet and sign a SIWE message
   - **Sign in with Google** — use your Google account (if configured)
2. Once signed in, navigate to **Secrets** or **Seals** to set up encryption
3. Choose a strong passphrase (minimum 8 characters) and save your encryption profile
4. Optional: Link additional authentication methods in your profile settings

## Running tests

Unit tests (Jest) run against an in-process Postgres (PGlite) with the real migrations applied — no setup needed:

```bash
bun run test                                          # Run all unit tests
```

End-to-end tests (Playwright) start their own native PostgreSQL process and dev server. Prepare the binaries explicitly once; Docker and a preinstalled database are not required.

```bash
bun run test:e2e:prepare                              # Download PostgreSQL + Chromium
bun run test:e2e                                      # Run all E2E tests
npx playwright test tests/specs/notes.spec.ts        # Run one file
npx playwright test --ui                             # Run with Playwright UI
```

The prepare command disables install scripts and explicitly restores PostgreSQL binary symlinks. Re-run it after upgrading Playwright or the pinned PostgreSQL version. On Linux CI, add `--with-deps` to install browser system libraries and run the suite as a non-root user.

Each run creates a fresh temporary database on an available loopback port, applies the real migrations, and shares it across parallel workers. Incoming `DATABASE_URL` and `TEST_DATABASE_URL` values are ignored. Teardown stops the owned processes and removes test data, including after setup failures. The app still reads its test settings from `.env.test`.

Other useful commands:

```bash
bun run lint     # ESLint + TypeScript type check
bun run format   # Prettier formatting
bun run build    # Production build
```

## Project structure

```
src/
├── app/                  # Next.js App Router pages and API routes
│   ├── api/
│   │   ├── encryption/   # Encryption profile and key material endpoints
│   │   ├── files/        # File upload and retrieval
│   │   ├── notes/        # Tier 1 CRUD
│   │   ├── secrets/      # Tier 2 CRUD
│   │   └── seals/        # Tier 3 CRUD
│   ├── secrets/          # Tier 2 pages
│   └── seals/            # Tier 3 pages
├── components/           # UI and feature components
├── config/               # Auth, wallet, and server configuration
├── contexts/             # EncryptionContext — MEK lifecycle management
├── controllers/          # Application logic over the database layer
├── db/                   # Drizzle: schema.ts, client.ts, tier.ts (shared tier repo)
├── hooks/                # TanStack Query data and mutation hooks
├── lib/
│   └── crypto.ts         # All client-side cryptographic operations
└── providers/            # App-wide React providers
```
